# 시작 지연 개선

2026-11-06에 코드와 기존 `~/.memoinall/desktop.log`를 확인하고 적용한 내용입니다.

## 확인한 원인

- 임베딩 모델 다운로드·로딩은 이미 백그라운드 스레드에서 실행되고 있었습니다.
- 벡터 행렬은 `store.vector_index()`를 호출하는 검색 시점에 읽습니다. 부팅 시 전체 벡터를 메모리에 올리는 구조는 아닙니다.
- FastAPI 시작 단계에서 `reindex_pending()`이 전체 메모의 재색인 대상을 동기로 조회했습니다.
- 실제 모델 로딩 중에는 현재 모델이 `hash-v1`입니다. 기존 쿼리는 저장된 의미 검색 벡터를 모델 불일치로 판단해 불필요하게 재색인할 수 있었습니다.
- 11월 6일 로그에는 13:49:10에 모델이 준비된 후 Windows `ProactorEventLoop`의 `accept`가 `WinError 64`로 실패하고, 13:49:38에 서버 시작 제한 시간에 도달한 기록이 있습니다. 이 경우 창을 띄우기 전에 약 30초를 기다렸습니다.

## 변경한 동작

1. 서버를 백그라운드에서 시작하면서 네이티브 준비 화면을 먼저 엽니다. 서버가 준비되면 메모 화면으로 연결합니다. 연결 실패도 같은 창에 표시합니다.
2. 준비 여부는 포트 연결만으로 판단하지 않고 가벼운 `/api/health`의 HTTP 응답으로 확인합니다. 로컬 요청에는 프록시를 사용하지 않습니다.
3. 데스크톱의 Windows 서버 스레드는 `SelectorEventLoop`를 사용해 로그에 나타난 Proactor의 accept 경로를 피합니다. 전역 이벤트 루프 정책은 바꾸지 않습니다.
4. 메모 API를 준비한 뒤 1초 후 모델 로딩과 재색인 조회를 시작합니다. 재색인 조회는 별도 스레드에서 실행해 요청 처리를 막지 않습니다.
5. 해시 임베더를 쓰는 동안에는 이미 보강된 의미 검색 벡터를 유지합니다. 실제 모델 준비 후 필요한 메모만 재색인하며, 전환 중 인코딩하던 메모도 새 모델로 다시 예약합니다. 명시적인 전체 재색인은 기존대로 동작합니다.
6. 사이드바는 의미 검색 준비 중에도 메모 작성·저장과 키워드 검색이 가능하다고 안내합니다.

## 배포

`python build_exe.py --onedir`로 `dist/memoinall/memoinall.exe`를 만듭니다.
`dist/memoinall` 전체를 함께 보관해야 합니다. 이번 빌드의 폴더 크기는 약 149MB이며 모델 가중치는 포함하지 않습니다.
기존 단일 파일 `dist/memoinall.exe`는 별도로 유지됩니다.

단일 파일 배포판은 Python 코드가 실행되기 전 임시 디렉터리에 구성요소를 풀어야 합니다.
이 시간은 앱 내부의 비동기 처리로 줄일 수 없으므로 폴더 배포 옵션을 제공합니다.
[PyInstaller 실행 방식](https://pyinstaller.org/en/stable/operating-mode.html)을 참고하세요.

## 검증과 측정 범위

- 시작 회귀 테스트 6개: 검색 준비를 강제로 지연해도 메모 저장·초안 복원·키워드 검색 가능, 기존 벡터 보존, 모델 전환 중 작업 복구, 창을 먼저 시작하는 순서, 실패·종료 처리, 실제 서버 HTTP 저장.
- API 검사 151개와 기존 브라우저 사용 흐름 통과. 빌드 옵션 테스트 6개, 데스크톱 검사 36개 및 종합 검사 55개 통과.
- 종합 검사는 첫 실행에서 할 일 검사 2개가 실패했지만 수정 전 저장 코드와 재실행한 현재 코드에서는 통과했습니다. 해당 테스트는 같은 메모에 백그라운드 보강과 직접 보강을 동시에 실행합니다. 데스크톱의 빈 포트 재바인드 검사도 한 차례 실패 후 재실행에서 통과했습니다.
- 별도 임시 DB에서 HTTP 준비 약 1.1초, 숨긴 실제 WebView2 입력창 확인 약 1.9초.
- 빌드된 폴더형 exe도 별도 임시 DB로 실행해 HTTP 응답과 메모 화면 제공을 확인했습니다. 실행 요청부터 확인까지 약 3.8초였습니다.

시간 측정은 모델 로딩을 비활성화한 테스트입니다. WebView2 측정은 라이브러리 import 이후부터이며,
exe 측정은 프로세스 실행 요청부터입니다. 실제 사용자 DB·모델을 포함한 콜드 스타트 개선 배수로 해석할 수 없습니다.
다음 실제 실행에서는 `desktop.log`의 메모 API 준비, 메모 화면 연결, 모델 준비 시간을 구분해 볼 수 있습니다.
